# Design notes

Why the model, the measures and the report look the way they do, and the traps I found on the way. The numbers and
the tables of columns are in [model.md](model.md); this file is about the choices.

## A project, not a `.pbix`

A `.pbix` is one binary file: Git cannot show what changed in it, and nobody can review it. A Power BI project
(`.pbip`) is a folder of text files: the model in TMDL, the report in PBIR (one JSON file per page and per visual). That
is what makes this repository possible: the model is generated by a script, tested by other scripts, and reviewed as text.

The price is that **two writers share the files**. My generator writes them once; from the first save in Power BI
Desktop they are Desktop's, and Desktop rewrites them in its own way (order of properties, annotations, identifiers).
So `labtrack-bi build` writes the project only the first time, `labtrack-bi check` stops comparing it byte by byte once
Desktop has saved it, and two other commands compare what the files **mean**: `check-model` for the model and
`check-report` for the visuals. The Power Query files, the DAX files, the documents and the drawings are mine only, and
are always compared byte by byte.

## The model

```text
Calendar ─┐
Study ────┼─> Session ─> Recording ─> Trial
Participant ┤                 ^
Researcher ─┘      Device ────┘
```

* **Star schema, filters in one direction.** `Calendar`, `Study`, `Participant` and `Researcher` filter `Session`;
  `Session` and `Device` filter `Recording`; `Recording` filters `Trial`. All seven relationships are many-to-one and
  single direction. A slicer on a study therefore cuts the sessions, the recordings and the trials of that study, and
  nothing ever flows back up, so no number depends on which visual happens to sit on the page.
* **One date, one path.** Only `Session[Session Date]` is related to `Calendar`. A recording or a trial reaches the
  calendar through its session. With three date columns related to the same table, two of the relationships would be
  inactive and every measure would need `USERELATIONSHIP`; with one path there is nothing to explain.
* **The calendar covers 2023 to 2028** (2,192 days), more than the data (March 2024 to December 2026), so that
  `SAMEPERIODLASTYEAR` has a previous year to look at, and it is marked as the date table. That is also why the charts
  by month are filtered to 2024-2026: the empty months would show.
* **Every key column is hidden** (the date of `Calendar` is the one exception: it is a date people use), and so is
  every column that exists only to sort (`Month No`, `Age Band Order`). A report author sees names, not `Study Key`.
* **One table of measures.** `Measures` has no data; it holds the 46 measures in six display folders (Counts, Sessions,
  Time, Recruitment, Quality, Findings), each with a format string and a description. The model sets
  `discourageImplicitMeasures`, so Power BI does not sum a column when someone drags it into a well: every number on a
  page is a measure that is written down.
* **No calculated columns.** Everything that shapes a column (labels, types, the year-month text) is done in Power
  Query, before the model sees it, so the model has nothing to recalculate on refresh but the measures.
* **One name in two places.** `Study[Target N]` is a hidden column and `[Target N]` is a measure. A column is always
  written with its table, a measure never is, so the two cannot be confused; the column is hidden so that nobody
  drags it into a chart and gets a sum that ignores the filters of the page.

## Power Query

* A parameter, `DataFolder`, holds the folder of the CSV files; every query reads from it. A reader changes one value
  instead of nine queries.
* Each query does the same steps in the same order: read the CSV, promote the headers, turn the empty cells into `null`,
  type the columns, rename, select. The conversion of types **passes the culture `en-US`**, so a computer with
  Brazilian regional settings (comma as the decimal mark) reads `1.5` as one and a half.
* `Table.ReplaceValue` turns `""` into `null` before the types are applied, because a `date` column with an empty cell
  would otherwise fail on refresh. I assumed that Power Query reads an empty CSV cell as `null`, which I could not test
  here; the step makes the queries right in both cases.
* Labels are made in Power Query too: `completed` becomes `Completed`, `no_show` becomes `No Show`
  (`Text.Proper(Text.Replace(...))`). The measures compare against those labels.

## The measures

Eight things that are not obvious from the list of measures:

1. **Distinct counts are not additive.** `Participants Attended` is a distinct count of people. Twelve of the 199
   participants took part in two studies, so the three studies add up to 211 and the total row of the table on page 1
   says 199. That is correct, and the note of the visual in [report-spec.md](report-spec.md) says why.
2. **Rates divide by closed sessions**, not by all sessions: a session in the future (15 are scheduled) is not a failure
   yet. `Completion Rate` is 817 of 894 closed sessions, which is 91.4%.
3. **`QC Pass Rate` leaves out the pending recordings**: a recording that has not been reviewed is neither a pass nor a fail.
4. **A running total is not a `DATESYTD`.** It is `CALCULATE([Sessions Completed], FILTER(ALL('Calendar'), 'Calendar'[Date] <= ThisDay))`:
   the `ALL` takes away the filter that the axis puts on the calendar, and the comparison puts back everything up to the
   end of the month. It is blank after the day of the last completed session (`REMOVEFILTERS('Calendar')` finds that
   day), so the line stops where the data stops, instead of staying flat into the months that have not happened.
5. **`Visit Retention` exists for one visit at a time.** It is blank (`HASONEVALUE`) unless the filter holds a single
   `Visit No`, because "came back compared with visit 1" means nothing for all the visits at once. The chart puts
   `Visit No` on its axis; the measure is in its tooltip.
6. **`CALCULATE(..., Session[Status] = "Completed")` replaces any filter on `Status`.** So `Sessions Completed` ignores a
   slicer on the status, which is what a measure with the word "completed" in its name should do.
7. **`BLANK` is a result.** A month without sessions has a blank `Sessions Completed`, not a zero. `BLANK() - 5` is
   `-5` in DAX, so the difference of two measures means something only where both have a value:
   `Feedback Effect on Force CV` is shown in a table filtered to the study FFB-01, where they do. Ratios use `DIVIDE`,
   which gives a blank, not an error, when the denominator is zero or blank.
8. **The findings use valid trials only.** A trial that was rejected in review does not count in `Mean Force CV`,
   `Mean MDF`, `Mean RMS` or `Mean Alpha Power`. The three effects (feedback lowers the variability of the force, fatigue
   lowers the median frequency and raises the RMS, a large stimulus lowers alpha power) are planted by the data
   generator of [labtrack-db](https://github.com/juanbezerra1/labtrack-db). They are **not science**.

A trap that was not in the measures: DAX query view and a report page do not use the same filters. `check.dax` evaluates
the measures with no filter at all, or with the group-by that the query names; the same measure on a page with a
slicer selected gives another number, as it should.

## The report

* **Four pages of 1280 x 720**, and 46 visuals. A margin of 16 pixels and a gutter of 8. The cards of a row share the
  width of the page equally; the title is a text box, because a report that will be seen on a screen by a stranger
  needs a title on the page itself.
* **One question per page.** Overview: how much was done. Recruitment: how many people, and how many came back. Data
  quality: where the data is weak. Findings: what the data says, with a text box that says that it is synthetic.
* **Every chart has its numbers.** Bars and columns with one series have data labels; a chart with two or more series
  has a legend; the tables carry the exact values of what the charts draw.
* **No dual axes, no pies, no donuts, at most four series.** Two measures with different scales go in two charts. A
  fifth series would be a fifth colour that a reader cannot tell from the fourth.

### Colours

The theme `LabTrack` has eight colours, in this order: `#2a78d6` blue, `#eb6834` orange, `#1baf7a` green, `#eda100`
amber, `#e87ba4` pink, `#008300` dark green, `#6250d6` violet, `#e34948` red; a page background of `#fcfcfb`; text
`#0b0b0b` and `#52514e`. A chart takes the colours in this order and never repeats one.

The palette was run through a validator (the script of the `dataviz` skill, with surface `#fcfcfb`):

| Check | Result |
|---|---|
| Lightness band, chroma floor | pass |
| Separation for colour-blind readers (neighbours in the list) | pass; the worst pair is amber and green (protanopia 9.1, tritanopia 5.8) |
| Separation for normal vision | pass; the worst pair is pink and amber (19.6) |
| Contrast with the background | **warning**: green 2.74, amber 2.11 and pink 2.62 are below 3 : 1 |

The warning is not dismissed, it is the reason for the rule above: a colour that is too light cannot be the only thing
that tells two series apart, so every multi-series chart has a legend, and every single-series bar or column chart has
labels. The two stacked charts (sessions by status, recordings by QC result) are the **weak spot**: they have a legend
and tooltips but no data labels, because small segments (15 scheduled sessions among 909) do not fit a label. If you
need them readable without colour, turn the labels on and accept the clutter.

## What is not here

Row-level security, incremental refresh, a deployment to the Power BI service, calculation groups for the time
intelligence, and a live connection to the [labtrack-db](https://github.com/juanbezerra1/labtrack-db) database. The CSV files
of `data/` are the export of its `medium` size, taken as they are; a model that reads from the database would use the
same tables.
